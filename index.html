Features

What's actually running

Double-layer AES-GCM-256

A per-file key encrypts the file; a separate Master Key encrypts that key and its metadata.

SRP-6a authentication

Zero-knowledge password proof — the server stores only a salt and verifier, never anything derivable back to your passphrase.

Pre-flight malware scan

The plaintext file is hashed locally; only the SHA-256 hash is checked against VirusTotal before encryption begins.

Direct-to-storage upload

Ciphertext uploads straight to Supabase Storage via a signed URL — never through a serverless function, so large files aren't capped at ~4.5MB.

One account, permanently

A database-level unique index makes creating a second account physically impossible — not just discouraged in the UI.

USB-portable mode

Evolved from a cloud-hosted Next.js/Supabase build into a fully offline tool with a separate decrypt utility for USB use.

Security

Things worth knowing before you rely on this

Stated plainly, not buried — every non-obvious trade-off in the design.

  • Malware scanning vs. zero-knowledge is a real tension. The default hash-lookup path leaks nothing but a SHA-256 digest and only catches previously-seen malware. Full-scan is opt-in and explicitly breaks zero-knowledge for that one file.
  • Browser memory can't be securely wiped. There's no mlock/explicit free in JS. Non-extractable keys plus prompt dereferencing is the practical best-effort — not a guarantee against local memory-inspection access.
  • PBKDF2, not Argon2id, is the default. Argon2id isn't in the native Web Crypto API; a stronger drop-in via hash-wasm is available if you want it.
  • The SRP library is smaller and less battle-tested than mainstream crypto primitives. Give it a security review before trusting it with something you can't afford to lose.
  • Free-tier Supabase pauses after 7 days of inactivity. The first request after a week away will fail until you reopen the dashboard once.
Threat model

What a stolen anon key actually exposes

Someone holding your public anon key — extractable from the deployed site's JS, since anon keys are meant to be public — could enumerate random object names in the storage bucket. They still can't read content or filenames without your Master Key and your private table.

Setup — no terminal, no card

  1. Supabase → free project → run sql/schema.sql in the SQL editor
  2. Storage → new bucket named vault-files → keep it Private
  3. Settings → API Keys → copy Project URL, service-role key, anon key
  4. VirusTotal → free account → copy your API key
  5. GitHub → new repo → paste every project file via the web UI (no CLI needed)
  6. Vercel → import the repo → add the 6 env vars from .env.example → deploy
  7. Open /setup once to create your account, then unlock at /
FAQ

Common questions

Can I create a second account later?

No — /setup permanently refuses after the first success, enforced at the database level.

What happens if I forget my passphrase?

There's no recovery path by design — the same passphrase authenticates you and derives your Master Key. Losing it means losing access to your files.

Does the malware scan see my file contents?

No, by default — only a SHA-256 hash of the plaintext is sent, checked against VirusTotal's existing database. Full-scan mode is opt-in and is the one path that breaks zero-knowledge for that file.
